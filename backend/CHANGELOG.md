### Fixed (later same day) — the "YES" timeout, and the misdiagnosed reissueOrder anomaly
- **`confirmEsdLineEdit()` waited unconditionally for a "YES" link that only sometimes exists.** User-reported with the verbatim error `locator.click: Timeout 30000ms exceeded — waiting for getByRole('link', { name: 'YES' })`. That YES is the *"this line will need to be re-issued"* warning, which MXI only raises when the edit genuinely forces re-issue/re-authorization; on an order that doesn't need it, the OK commits and the page returns straight to RO Details, so the code waited 30s for a dialog that was never coming and then threw — **on a write that had already succeeded**.
  - **This resolves the long-documented "reissueOrder() reliability gap"**, which was a misdiagnosis. A real 40-order run had recorded thrown exceptions where the ESD nonetheless committed correctly, and that was attributed to `reissueOrder()`. It was actually this, one step earlier. `docs/PHASE2_MXI_WRITER_SPEC.md` now carries a correction above the original addendum (kept unedited — its observations were accurate, only the attribution was wrong).
  - Now waits for a **definitive end state** — YES present (click it), or already back on RO Details (nothing to confirm) — rather than assuming the warning always appears. Same content-aware-wait discipline as `waitForUnassignedTasksSectionResolved`, and the same conditional-YES precedent that `writeUps/shared/authFlow.ts` had been using all along but which was never applied here.
  - Deliberately does not throw when neither marker resolves: every caller independently re-verifies the real committed value, so a slow page becomes a verification failure with evidence rather than a spurious timeout on a working write.
  - The identical unconditional-wait shape in `reissueOrder()`'s trailing "OK" got the same treatment.
  - **Affects three features**, all of which share this selector: Invoice Price Writer, Vendor Quote Writer, and the ESD writer (`writeEsdAndNotes`). Whether the re-issue warning appeared is now recorded per row in the price writers' `issueDetail`.

### Fixed (later same day) — "the BER/X buttons and the write button do nothing"
- **Root cause was a stale backend process, not a UI bug.** User-reported: the BER and X buttons appeared inert, and the write confirmation dialog did nothing on Yes. Diagnosed by probing the *running* server rather than reading code: `/api/quotes/active-job` returned 401 (route present) while `/api/quotes/write` and `/api/quotes/extractions/:id/disposition` returned **404** — the server process had been started at 14:45, before those two routes existed. Reads worked because their routes predated it. Restarted; all three now return 401 (present and session-gated).
- **The real defect this exposed is that a failed request was invisible.** Both handlers already caught the error and set a banner — but the banner renders at the top of the page while the row-level BER/X buttons sit far down a long table, so a genuine 404 looked exactly like a button that did nothing. Two fixes: errors now scroll themselves into view (and are dismissable, with an icon), and a 404 on one of this tab's own endpoints reports the actual likely cause — "the API server is running an older build than this page — restart it" — instead of a bare `Request failed (404)`. Paths here are hardcoded and proxied same-origin, so a 404 essentially never means "wrong URL"; it means version skew.
- No change was needed to the disposition or write logic itself, which was correct.

### Added (later same day) — Vendor Quote Writer stage 5: the MXI write
- **Approved quotes now write to MXI**: Unit Price + Price Type=`QUOTE` + Promise By set to the ESD derived from the vendor's own quote — then, and only then, the source email is marked read.
  - **Reuses `writePriceLineUpdate()` rather than reimplementing the write.** That function is already live-proven and carries the serial-number cross-check, the integer-cents price comparison, and the always-re-verify discipline. It gained one optional `promiseByDate` parameter — **omitted, its behavior is byte-for-byte what the Invoice Price Writer already did** (tomorrow), so adding this second caller changes nothing about the live first one.
  - **Four structural guards in `quoteWriteRunner.ts`, none depending on the caller behaving**: (1) effective disposition is re-read from the DB, so an NREP/BER/excluded row cannot be written even if its id is passed explicitly; (2) `quoteExtractionAlreadyWritten()` blocks a second successful write, since re-writing reissues the order again for nothing; (3) rows missing an order number, price, serial, or ESD are skipped — no partial writes; (4) mail is marked read only after a verified-successful write, so a failure leaves the item in the unread queue rather than silently losing it.
  - A successful write whose *email* couldn't be marked read is reported as a **success with a footnote, not a failure** — the price and ESD really did land, and calling it failed would invite a "retry" of a write that already happened. `quote_writes.write_status` and `quote_writes.marked_read` are separate columns for exactly this reason.
  - New `POST /api/quotes/write` (session-gated, `env` required and never defaulted) plus a `Write N to MXI` button, environment selector, confirmation dialog, and per-row write-status column in the UI. New `npm run quote:write` CLI (`list` shows what is and isn't writable and why; `write` needs `--confirm`) specifically so the first real write against an environment can be done deliberately, one order, watched from a terminal.
  - **Verified**: endpoints registered and 401 unauthenticated; the `list` view correctly flipped two rows to blocked once marked BER and excluded, and a `write` explicitly naming a BER order **refused the whole request**; and the mark-as-read mutation was round-tripped for real against a live message (flipped unread, script marked it read, independently re-read to confirm, second call correctly reported `alreadyRead` — message left in its exact original state, net zero change to the mailbox).
  - **NOT yet exercised: a real MXI write.** Every guard around it is tested, but no price or ESD has actually been pushed to stage or production by this path. Per this project's standing discipline for a new kind of production action, the first one should be a single order, watched.

### Added (later same day) — Vendor Quote Writer: NREP / BER / exclude dispositions
- **Three distinct quote dispositions, deliberately not collapsed into one boolean** — they have different origins and different authorities. `excluded_nrep`: the VENDOR said the part is non-repairable, read off their document and applied automatically. `excluded_ber`: the CRA judged it Beyond Economical Repair — a PSA-side commercial call only a human may make. `excluded_other`: a plain "not this one" X, no reason required or recorded. Both scrap reasons are what a future scrap workflow will key on; `excluded_other` deliberately is not, since "skip this" says nothing about the part's condition. **The scrap process itself is explicitly out of scope** — this only records the signal.
  - NREP auto-excludes from the MXI write per user direction (no repair means no repair to price), but it is a default, not a lock: an analyst who disagrees with the model's read can set the row back to `pending`, recorded as their decision.
  - Human decisions live in a new append-only `quote_dispositions` table (latest row wins), same shape as `mxi_writes`/`write_up_issue_decisions`, so who decided what and when stays auditable rather than overwritten. The vendor-derived NREP flag lives on `quote_extractions` instead, because it's an extraction fact, not a decision. `POST /api/quotes/extractions/:id/disposition` **refuses `excluded_nrep`** — letting a client assert it would fabricate a vendor claim that was never made.
  - **REAL GAP FOUND AND CLOSED**: the extractor read only the PDF, subject, and filename, but a genuine message in the live folder states a scrap decision *only in the email body* ("The scrap fee for P000BCSG ... is $360") with nothing about it in the attachment. The body is now real extraction input (truncated to 6000 chars server-side). This matches the user's own framing — non-repairable arrives "in the email **or** the quote."
  - **Detection validated 5/5 on a controlled positive/negative suite** against a real quote PDF with varying bodies, including the two cases that matter most: an *expensive but repairable* quote is correctly NOT flagged (BER must stay a human judgement, never inferred from a big number), and a scrap fee quoted for a *different* order in a reply chain does not leak onto the attached quote. Both positives correctly produced `excluded_nrep` → not writable. Confirmed independently against real mail too: `P000B8V5` was correctly left writable despite "scrap" appearing in its body, because that text referred to other orders.
  - **Known extraction variability, stated plainly**: across five real runs of the same PDFs, prices were perfectly stable (`2157`, `196`, `3116.35` identical every time), but `P000BEGR`'s completion date came back `2026-08-20` on three runs and `null` on a fourth, shifting its derived ESD by 5 days. Not blocking — every row is human-reviewed before any write — but real, and worth knowing before trusting a date unattended.

## 2026-08-15

### Added
- **[#6-hardening][key-rotation] Key rotation / re-encryption tooling — Seam 2, per explicit user direction: eliminate the "lose `CREDENTIAL_ENCRYPTION_KEY` = every stored MXI password permanently undecryptable" risk, and build the rewrap mechanic the future Key Vault migration reuses.** Zero change to normal runtime behavior — a new offline utility + a backward-compatible ciphertext format, nothing about how the live app encrypts/decrypts today.
  - **Part A — version tag, not a `key_version` column.** Chosen over a schema column specifically because it's less invasive against the current format (`auth/crypto.ts`'s `iv:authTag:ciphertext`): zero `ALTER TABLE`, self-describing (can't drift the way a separate column could), and generalizes better to the Key Vault future (Key Vault has its own native secret versioning; an app-level AES-specific integer column wouldn't carry over). New format: `v<N>:iv:authTag:ciphertext` — `decryptSecret()` parses both the tagged and legacy untagged form transparently, so every existing row (implicitly "v1," no tag) keeps decrypting exactly as before, no forced migration. `encryptSecret()`'s default behavior (every existing call site — `authService.ts`'s `register`/`changePassword`) is **left byte-for-byte unchanged** — still emits the untagged format; only `rotateEncryptionKey.ts` ever writes a tagged value. `// NOTE:` comment added at that decision point: new writes stay untagged until Seam 3 tags `register`/`changePassword` with an explicit `v1` marker, since `authService.ts` will already be under edit there.
    - `crypto.ts`'s `encryptSecret`/`decryptSecret` both gained a small, additive, optional parameter (`keyOverride` for both; `version` to emit for encrypt) — verified exactly 3 existing call sites (all in `authService.ts`), all still calling with just the original single argument, reproducing today's exact output. - **[#6]** Real regression found via an actual browser-driven test (Playwright, not just typecheck) after wiring auth in: `ExecuteRunProvider` (tracks in-progress execute jobs so they survive page reloads) does a one-shot, ref-guarded "re-attach to an already-running job" check on its own first mount, never retried.
