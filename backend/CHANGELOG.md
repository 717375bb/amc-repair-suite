- **[#6]** Three real security gaps closed before writing `security.md`, per explicit user direction ("gaps closed where possible... document drafted first, then revised" — the doc below reflects the state *after* these fixes, not before):
  1. **Timing-safe automation-key comparison** (`backend/src/server.ts`'s `requireAutomationKey`) — was a plain `!==` string comparison, which leaks timing information proportional to how many leading characters match. Now `crypto.timingSafeEqual`, guarded by an explicit length check first (`timingSafeEqual` throws on mismatched lengths — the guard is required, not a shortcut).
  2. **Login rate limiting + lockout** (new `backend/src/auth/loginRateLimit.ts`) — login previously had zero brute-force protection (unlimited password guesses, no delay). Now: 5 failed attempts for a given username within 15 minutes locks that username out for 15 minutes, checked *before* password verification (so a locked-out guess never pays the scrypt cost) — confirmed via real test that the 6th attempt is rejected even with the *correct* password, so a lockout can't be distinguished from "about to succeed" by an attacker.
  3. **Auth audit trail** (new `auth_events` table, `backend/src/db/authDb.ts`) — every register/login success/login failure/lockout/logout/password change is now recorded (username + event type + timestamp, never credential material) via `insertAuthEvent`, wired into every relevant handler in `authRoutes.ts`.
  - All three verified with a real 15-check test against the live Express app (correct/wrong/empty/missing automation keys; 4 failed logins still 401, 5th still 401, 6th locked out with 429 even using the real password; `auth_events` contains exactly the expected register/5×login_failure/1×login_locked_out rows, all against the real username) — not just typechecked. Throwaway test script deleted after use.
- **[#6]** Real login/account system — the first concrete piece of the security overhaul, scoped to this session's specific ask (a login page + account creation), not the full `[#6]` item from the original ground rules (security.md, privacy policy, enterprise-grade restructuring are still not started).
  - **New auth database** (`backend/src/db/authDb.ts`, `data/auth.db` — deliberately separate from `data/audit.db`, a different sensitivity class and a smaller, focused table for the user's own planned future Azure migration). One `users` table: `username` (UNIQUE — enforces "no repeat credentials" at the DB level, confirmed with a real duplicate-registration test), `password_hash`, `mxi_password_encrypted`.
  - **Two different crypto primitives for two different jobs** (`backend/src/auth/crypto.ts`, Node's built-in `crypto` only, no new dependency, per explicit user preference): `scrypt` for the login password (one-way, confirmed by the user) — but scrypt can't be reversed, and the MXI writer needs the *real* password to type into MXI's login form, so the same password value is *also* stored via reversible AES-256-GCM under a separate master key (`CREDENTIAL_ENCRYPTION_KEY`, new `.env` var, documented in `.env.example` with the generation command).
  - **One identity, not two**: per explicit user direction, the login username *is* the literal MXI username and the login password *is* the literal MXI password — confirmed no separate "app password" concept anywhere in the design.
  - **Change password** (`backend/src/auth/authService.ts`'s `changePassword`, `/api/auth/change-password`, `src/pages/ChangePassword.tsx`) — requires the current password (not a token/email reset — no email infrastructure exists, and knowing the current password is the right bar here per explicit user direction: "old password, new password, confirm"). Updates both the login hash and the encrypted MXI credential together so they can never drift to different underlying passwords.
  - **Sessions** (`backend/src/auth/sessions.ts`): in-memory (same accepted v1 tradeoff as `jobManager.ts`'s own job registry — a restart logs everyone out, fine for a local tool), httpOnly cookie, `SameSite=Lax`, no `Secure` (this server is 127.0.0.1 plain HTTP by design — a `Secure` cookie would be silently dropped and login would appear to succeed then immediately fail).
  - **`requireSession` replaces `requireAutomationKey`** on every browser-UI route (`/api/vendors`, `/api/discovery`, `/api/execute`, `/api/runs/*`, `/api/esd/*`) — per explicit user confirmation, the Power-Automate-facing endpoints (`/pending-esd-updates`, `/esd-updates/:orderNumber/{approve,reject}`) deliberately keep `AUTOMATION_API_KEY` unchanged, a genuinely different machine-to-machine trust boundary. Verified directly (not assumed) that a valid session alone does NOT satisfy the automation-key gate and vice versa.
  - **Per-user MXI credentials actually reach the Playwright writer.** This required tracing the real call path, not just gating routes: Order Write-Ups' discovery/execute and ESD Finder's write job are spawned CHILD PROCESSES (`jobManager.ts`/`esdFinderJobManager.ts`'s `spawnRunner`) that independently read `MXI_STAGE_USERNAME`/`MXI_STAGE_PASSWORD`/`MXI_PROD_USERNAME`/`MXI_PROD_PASSWORD` from their own inherited environment (`cliMxiClient.ts`) — before this change, every spawned job silently used whatever was in the server's own static `.env`, regardless of who was using the UI. `spawnRunner` gained an optional `envOverrides` parameter (merged over, never replacing, `process.env`), and `startDiscoveryJob`/`startExecuteJob`/`startEsdWriteJob` now require an `MxiCredential` argument, decrypted from the logged-in session's own stored credential (`getMxiCredentialForUser`) and injected as both the STAGE and PROD pairs — "one per user, same for stage and prod," per explicit user direction. ### Fixed
- **[#6]** Real regression found via an actual browser-driven test (Playwright, not just typecheck) after wiring auth in: `ExecuteRunProvider` (tracks in-progress execute jobs so they survive page reloads) does a one-shot, ref-guarded "re-attach to an already-running job" check on its own first mount, never retried. It used to live at the app root (`main.tsx`), wrapping every route including `/login`. With login now always gating the very first page load, that one-shot check's first (and only) mount was now always anonymous — a silently-swallowed 401, permanently losing the reconnect feature for the rest of the session, every time. Moved `ExecuteRunProvider` into `RequireAuth`'s guarded tree instead, so its first real mount happens exactly when login succeeds.
- **[#6]** **Real, user-reported bug: every action after login (vendor list, ESD Finder file upload, etc.) failed with "Not logged in," even though login/account creation themselves worked.** Root cause: the browser (`localhost:5173`) was calling the backend directly cross-origin (`http://127.0.0.1:3001`) — `localhost` and `127.0.0.1` are different *hosts*, which browsers treat as a different "site" for cookie purposes even though both are loopback. The session cookie's `SameSite=Lax` silently drops on cross-site fetch/XHR calls (only the request that originally sets it — login/register — is unaffected, since that's not about sending an existing cookie). CORS itself was configured correctly the whole time, which is why this wasn't a CORS error — it was a clean, correctly-formed 401. **This was misdiagnosed in this same session's earlier "Verified" notes below as a low-severity, dev-mode-only artifact** — the diagnostic evidence (a request with no Cookie header at all) was right there, but its real-world impact was underestimated. Corrected now, not left standing. Fixed properly: added a Vite dev-server proxy (`vite.config.ts`, `/api` → `http://127.0.0.1:3001`) so the browser only ever talks to its own origin — no cross-site relationship exists at all, regardless of which loopback hostname the app is opened at. `lib/api.ts`/`lib/esdFinderApi.ts`/`lib/authApi.ts`'s `BASE_URL` now defaults to `''` (same-origin relative path) instead of the hardcoded absolute URL; the real `.env.local`'s `VITE_API_BASE_URL` override (which would have silently defeated the proxy fix) was removed, along with the now-fully-unused `VITE_AUTOMATION_API_KEY`. Re-verified with a fresh browser-driven test reproducing the exact reported symptoms (register → Order Write-Ups vendor list renders real rows → ESD Finder file upload reaches real parsing logic, not an auth wall) — zero 401s observed anywhere after login, versus the prior test run which had one at the exact same code path this fix targets.

- **[#4a]** ESD Finder file ingestion (`backend/src/api/esdFinder/ingestion.ts`) no longer fails real dropped files. Root cause was NOT a title-row-position issue (that theory, from a synthetic test file, didn't hold up against a real one) — it was two separate real bugs, confirmed against a genuine file (`08-12-2026 Brayden Bury OOR.xlsm`, sheet `VendorOrders`, 1933 rows):
  1. **Hardcoded sheet-name lookup.** `readRealHeaders()` called `getWorksheet('Vendor OOR')` / `getWorksheet('CRA OOR')` literally — a real export named its sheet `VendorOrders` instead, so the lookup returned `undefined` and the old code silently handed back an empty header set (every required column then reported "missing," regardless of actual content). Replaced with `resolveAndValidateSheet()`: resolves the real data sheet by CONTENT (whichever worksheet's row-1 headers, after aliasing, satisfy the required column list for the schema being checked), falling back to the first/only worksheet if no sheet matches by content. The silent empty-Set early-return is gone — if a workbook has no worksheets at all, it now throws a clear error naming what it looked for. The previously-planned "scan first 5 rows for a title row" idea was dropped entirely per the user — row 1 is confirmed to always be the true header row.
  2. **Header-name drift.** The real file's CRA-shaped headers (`TAT`, `Order Status`, `Notes`, `RO ESD`) match `CRA_OOR_REQUIRED_HEADERS` exactly except `RO ESD` where the code expects `MXI RO ESD`. Added `CRA_OOR_HEADER_ALIASES` (`backend/src/parsers/craOorParser.ts`) — a small, explicit `{ 'RO ESD': 'MXI RO ESD' }` map — and threaded an optional `headerAliases` parameter through `readSheetRows()` (`sheetUtils.ts`, default `{}`, so every other caller — Vendor OOR, Vendor Assignments, the CLI path — is unaffected) so the alias applies both at validation time AND at actual data-parse time. Verified this matters: without threading it into the parse itself, `parseCraOor`'s `get('MXI RO ESD')` would have returned `null` for every row even after validation passed — the exact "looks complete, one field is silently null" failure mode this project has been burned by before. Confirmed via a synthetic single-row test that the alias genuinely carries a populated value through (`"RO ESD": "15-AUG-2026"` → `mxiRoEsd: "15-AUG-2026"`), not just structurally-present-but-null. The alias is scoped to CRA OOR only — Vendor OOR's own legitimate `RO ESD` column (a different field, the vendor's promised ship date) is never aliased.
  3. **Type detection.** `resolveAndValidateSheet()` also tries the *other* known OOR schema before giving up, so a CRA-shaped file validated under `role="vendor"` now gets a specific "expected VENDOR OOR but this matches CRA OOR instead (sheet X)" error instead of a generic wall of "10 headers missing."
  - Real-file re-test after the fix: `role="cra"` now resolves sheet `VendorOrders` by content, applies the alias, and parses 1933 rows successfully (`role="vendor"` correctly still rejects it, now with the specific cross-schema message). This file's real `RO ESD` column happens to be empty on every row (confirmed independently against the raw sheet, not just the parser output) — so this is a genuine property of the file, not a residual bug.
  - `parseVendorOorFileWithValidation`/`parseCraOorFileWithValidation` also stopped independently re-guessing a hardcoded sheet name for the actual data parse — they now parse the exact sheet validation just resolved.
  - Temp diagnostic logging (gated behind `ESD_FINDER_DEBUG_HEADERS=1`) stays in `ingestion.ts`, moved into `resolveAndValidateSheet()` and fixed to always fire before any resolution decision (previously it sat after the early-return and could be silently skipped in exactly the failure case that mattered).
  - Real vendor data files (`08-12-2026 Brayden Bury OOR.xlsm`, `Week of 08-10-2026 MEASURETECH INC OOR.xlsx`) ended up directly under `backend/` this session (outside the gitignored `data/` dir) — flagged to the user, not staged, `.gitignore` fix or manual move still pending.
