### Added
- **Cancel button (ESD Finder + Order Write-Ups)** — a visible Cancel control during any active run (discovery/execute for Order Write-Ups; compare/write for ESD Finder), gated behind a confirmation dialog, plus persistent run state so navigating between tabs mid-run no longer loses progress or the cancel control. Real, end-to-end backend cancellation, not a frontend-only "stop watching":
  - **Cooperative cancellation, not process signals** (`backend/src/api/jobRunners/cancellationWatcher.ts`): this project runs on Windows, where `ChildProcess.kill()` force-terminates immediately regardless of signal argument — a runner mid-Playwright-session would have zero chance to call `client.shutdown()`, risking an orphaned headless Chromium process still holding a real MXI login. Instead, the parent writes a single `{"type":"cancel"}` JSON line to the runner's stdin (`spawnRunner`'s stdio changed from `['ignore','pipe','pipe']` to `['pipe','pipe','pipe']`); every runner that opens a real MxiClient (discovery, execute, esdWrite — not esdCompare, which never touches a browser) checks the resulting `AbortSignal` between lines/vendors/orders, never mid-action, so its own existing `finally { await client.shutdown() }` still runs on a normal early-return. `jobManager.ts`'s `requestCancellation()` still keeps a 10s grace-period hard-kill fallback for a runner that never reaches its own next checkpoint — accepted as a rare last resort, not the primary mechanism.
  - **New `'cancelled'` job status** (`JobStatus`/`EsdJobStatus`), distinct from `'failed'`. `cancelJob()`/`cancelEsdJob()` set it synchronously the moment cancellation is requested (so a poll immediately after already sees it, without waiting for the child to actually exit) and free the job slot immediately; the runner's own exit handler checks `cancelRequested` first, before fatalError/exit-code, so a runner that exits 0 after honoring a cancel is still recorded as cancelled, never completed.
  - **Two new endpoints**, same `requireSession` gate as every other browser-UI route: `POST /api/runs/:runId/cancel`, `POST /api/esd/runs/:runId/cancel`.
  - **Cancel semantics, per explicit user direction**: cancelling a *read* (discovery/compare) discards it entirely — nothing was written, nothing to preserve. Cancelling a *write* (execute/esdWrite) does NOT discard anything — lines/orders that already completed keep their real results untouched; the run returns to its review screen with only the not-yet-attempted lines re-offered, never the already-completed ones (a deliberate choice, confirmed with the user, over restoring the full original selection — re-offering an already-completed line would risk creating a duplicate real order).
  - **`targetLineCount`/`sourceCompareRunId` added to the job registries** (`jobManager.ts`'s `Job`, `esdFinderJobManager.ts`'s `EsdJob`) — real gaps found while building the "return to review after cancel" flow: neither the original target-line count nor (for ESD Finder writes) which compare run a write came from was previously exposed anywhere the frontend could recover after a fresh page reload mid-run, only from data the page itself happened to still hold in memory.
  - **Frontend**: `lib/executeRun.tsx` (execute-only) replaced by `lib/orderWriteUpsRun.tsx` (discovery + execute) and new `lib/esdFinderRun.tsx` (compare + write) — both mounted in `components/RequireAuth.tsx` (same reasoning as the original ExecuteRunProvider: only meaningful once a session exists). Both pages' line/order selection state was restructured from "the selected set" to "deselections from an implicit default-all-selected baseline, computed at render time" — the original design re-initialized selection via a `useEffect` on phase transitions, which `eslint-plugin-react-hooks`' `set-state-in-effect` rule correctly flagged (a setState directly inside an effect, even ref-guarded to fire once); computing "selected = eligible minus deselected" at render time needs no effect at all, and a new, smaller eligible set (e.g. after a cancel) is correctly all-selected for free. New shared `components/ConfirmDialog.tsx`, extracted from the same visual pattern already proven in `EnvironmentBar`'s inline "Switch to Production?" dialog (that original stays untouched, per the same "don't risk regressing an already-working confirm" reasoning that motivated pulling `EnvironmentBar` itself out earlier).

Backend server boots cleanly with the new routes wired in and correctly gated (`POST /api/runs/:runId/cancel` and `POST /api/esd/runs/:runId/cancel` both return a real `401` unauthenticated, same as every other session-gated route) — checked against an isolated port, not the already-running instance on the default port, to avoid disturbing it. ### Fixed
- **Real bug, user-reported and reproduced same-day: every run silently hung on the UI after headless was turned off to debug the Akamai issue.** Root cause traced directly, not guessed: `spawnRunner`'s stdio change above (`'ignore'` → `'pipe'` on stdin, needed so the parent can send a cancel message) meant `cancellationWatcher.ts`'s `readline.createInterface({ input: process.stdin })` now put a REAL pipe into flowing mode — an active handle that keeps a Node process alive in its own right, independent of whatever else the process is doing. A runner's real work could finish completely (real MXI login, real search, real results found, `client.shutdown()` genuinely closing the browser, a `'done'` envelope written to stdout) and the child process would still never exit, because this one open stdin listener alone kept the event loop alive waiting for input that was never coming. From `jobManager.ts`'s side (which only marks a job finished on the child's `close` event) this looked exactly like a hang — the run had actually succeeded, but nothing ever reported it. Reproduced directly: spawned `discoveryRunner.ts` exactly as `jobManager.ts` does, against a real vendor in production — stdout showed a clean `'done'` envelope with real found lines, but `close` never fired. Fixed with a single `process.stdin.unref()` right after creating the readline interface — tells Node this handle shouldn't count toward keeping the process alive, so the listener can still react to a real cancel message while other real work is in flight, but no longer blocks a normal exit once that work is done. Re-verified with the identical reproduction: clean `[exit] 0` after ~14s, matching normal run time.
- **Incidental, real, and separately significant**: this same debugging session confirmed turning off `HEADLESS` fixed real MXI login (previously failing with the Akamai "Access Denied" edge block noted earlier today) — strong evidence the block was specifically fingerprinting/rejecting headless Chromium traffic, not blocking this server's IP/traffic outright. Login now succeeds headed; the stdin-hang bug above was the next, previously-unreached failure once login started working again. `HEADLESS=false` is now set in `backend/.env` (temporary, for this debugging — flip back once done, since a permanently headed run leaves a visible browser window open on whatever machine runs the server).

- **[#6]** Three real security gaps closed before writing `security.md`, per explicit user direction ("gaps closed where possible... document drafted first, then revised" — the doc below reflects the state *after* these fixes, not before):
  1. **Timing-safe automation-key comparison** (`backend/src/server.ts`'s `requireAutomationKey`) — was a plain `!==` string comparison, which leaks timing information proportional to how many leading characters match. ### Fixed
- **[#6]** Real regression found via an actual browser-driven test (Playwright, not just typecheck) after wiring auth in: `ExecuteRunProvider` (tracks in-progress execute jobs so they survive page reloads) does a one-shot, ref-guarded "re-attach to an already-running job" check on its own first mount, never retried. It used to live at the app root (`main.tsx`), wrapping every route including `/login`. With login now always gating the very first page load, that one-shot check's first (and only) mount was now always anonymous — a silently-swallowed 401, permanently losing the reconnect feature for the rest of the session, every time. Moved `ExecuteRunProvider` into `RequireAuth`'s guarded tree instead, so its first real mount happens exactly when login succeeds.
- **[#6]** **Real, user-reported bug: every action after login (vendor list, ESD Finder file upload, etc.) failed with "Not logged in," even though login/account creation themselves worked.** Root cause: the browser (`localhost:5173`) was calling the backend directly cross-origin (`http://127.0.0.1:3001`) — `localhost` and `127.0.0.1` are different *hosts*, which browsers treat as a different "site" for cookie purposes even though both are loopback. The session cookie's `SameSite=Lax` silently drops on cross-site fetch/XHR calls (only the request that originally sets it — login/register — is unaffected, since that's not about sending an existing cookie). CORS itself was configured correctly the whole time, which is why this wasn't a CORS error — it was a clean, correctly-formed 401. **This was misdiagnosed in this same session's earlier "Verified" notes below as a low-severity, dev-mode-only artifact** — the diagnostic evidence (a request with no Cookie header at all) was right there, but its real-world impact was underestimated. Corrected now, not left standing. Fixed properly: added a Vite dev-server proxy (`vite.config.ts`, `/api` → `http://127.0.0.1:3001`) so the browser only ever talks to its own origin — no cross-site relationship exists at all, regardless of which loopback hostname the app is opened at. `lib/api.ts`/`lib/esdFinderApi.ts`/`lib/authApi.ts`'s `BASE_URL` now defaults to `''` (same-origin relative path) instead of the hardcoded absolute URL; the real `.env.local`'s `VITE_API_BASE_URL` override (which would have silently defeated the proxy fix) was removed, along with the now-fully-unused `VITE_AUTOMATION_API_KEY`. Re-verified with a fresh browser-driven test reproducing the exact reported symptoms (register → Order Write-Ups vendor list renders real rows → ESD Finder file upload reaches real parsing logic, not an auth wall) — zero 401s observed anywhere after login, versus the prior test run which had one at the exact same code path this fix targets.
